# 架构与模块边界规范

## 1. 分层

采用“输入/命令 → 领域规则 → 状态变化 → 事件 → 表现”的方向。输入层不直接修改最终状态；表现层不决定领域规则；数据资源描述配置，不保存运行时可变状态。

## 2. 模块职责

- `core`：运行会话、流程状态、事件分发、时间抽象、存档服务；不实现具体武器或敌人规则。
- `player`：玩家输入适配、移动、属性、生命和背包；不决定掉落、关卡通关或 UI 布局。
- `combat`：攻击、伤害、状态效果、敌人和 Boss；不直接写入 UI 或存档。
- `world`：地图、房间、迷雾、刷新、安全区、驻留惩罚和关卡目标；不管理局外成长。
- `progression`：局内升级、局外成长、难度和复活；不读取节点树寻找玩家内部字段。
- `items`：物品定义/实例、资源、特殊武器和陷阱；不直接推进关卡。
- `presentation`：HUD、菜单、反馈、动画和音效；只消费状态/事件并发出用户命令。
- `scenes`：组合节点和注入依赖；避免把领域计算写进场景脚本。

## 3. 依赖规则

允许上层调用下层公开接口；禁止访问下层内部变量、依赖具体节点路径或通过字符串反射调用未知方法。跨模块通信优先使用明确接口或语义稳定的事件。新增依赖必须在开发计划或任务报告中说明。

## 4. 全局服务

Autoload 只能用于真正跨场景且生命周期明确的服务，例如会话状态、事件总线、存档服务。禁止把玩家、敌人、UI 或所有业务规则塞进单一 Autoload。每个 Autoload 必须有职责说明、初始化/关闭行为和测试。

## 5. 原型阶段

原型允许简化表现和地图内容，但不得以原型为由复制核心规则、绕过接口或把临时变量写成跨模块隐式契约。原型代码若预计保留到正式阶段，必须按正式边界命名和组织。
