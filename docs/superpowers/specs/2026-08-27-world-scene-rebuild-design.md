# 区域重建与多地图快照恢复设计

## 背景

当前安全退出快照已经保存运行级模型和实体状态，但恢复入口没有稳定的“当前地图”来源。主场景固定为地下室，导致从其他楼层退出后无法可靠重建原地图；楼层边界快照也尚未自动接入离层流程。

## 目标

1. 为每个楼层提供显式、可测试的场景目录映射。
2. 在成功离层前自动写入当前楼层边界快照。
3. 读取安全退出或边界快照时，校验并保留当前场景标识、路径和出生点。
4. 提供恢复并切换到正确场景的入口，场景组装完成后再应用实体快照。
5. 地图路径缺失、非法楼层、场景不匹配或重复恢复时安全拒绝。

## 方案

新增纯模型 `WorldSceneCatalog`，维护楼层号、场景 id、场景路径和默认出生点。当前灰盒内容映射为：1 层地下室，2-5 层慈航郊外，6 层终局核心；后续正式地图只需替换目录配置，不改 GameManager 的恢复流程。

GameManager 在注册运行场景时记录 `scene_id`、`scene_path` 和 `spawn_point_name`。创建快照时把这些字段放入已有 `run_session_state` 字典；`RunSessionModel` 对未知嵌套字段保持向后兼容。恢复时若快照缺少位置元数据，则按楼层号从目录推导；若元数据存在但路径不是目录允许值，拒绝恢复。

`depart_floor()` 在消费逃生物资和推进楼层前自动写入当前楼层边界快照。这样边界快照代表“已完成当前楼层、尚未提交下一层”的安全位置，切换失败时仍可重试离层。安全退出恢复继续使用现有主快照优先、边界快照回退规则。

新增 `restore_safe_exit_to_scene()`：先恢复运行模型，再根据保存的位置路径调用现有 `change_scene()`；目标场景由 `WorldSceneController` 注册并在 deferred 阶段应用待恢复玩家、敌人和交互状态。错误场景不会消费待恢复状态。

## 错误处理

- 楼层号不在目录范围：恢复失败。
- 场景路径为空、资源不存在或与目录 id 不一致：恢复失败。
- 当前运行非空闲时重复恢复：返回 `false`，不修改现有运行。
- 目标场景尚未完成动态实体组装：保留待恢复状态，下一次场景注册继续尝试。
- 边界写入失败：`depart_floor()` 返回 `false`，不消费逃生物资、不推进楼层。

## 测试策略

- 目录模型覆盖有效楼层、非法楼层、路径/id 双向查询。
- 存档集成覆盖第二层场景位置保存、重置后恢复路径、场景加载后实体状态回填、边界自动写入、重复恢复、非法场景元数据和边界写入失败。
- 既有模型、场景、框架、编辑器和主场景验证继续作为回归门槛。

## 非目标

- 不实现正式随机地图生成器、地图资源热加载、云存档、旧 schema 迁移或网络同步。
- 不修改生存、灾难、Boss、库存和随机流规则。
