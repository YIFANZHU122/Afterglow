# 启动流程、镜头跟随与局内 Buff 系统设计

## 1. 背景

当前项目的主场景直接指向地下室，世界场景在运行空闲时自动开始一局，因此没有正式开始界面。玩家场景虽然已经拥有 `Camera2D`，但镜头平滑跟随被关闭，实际体验不像以玩家为中心的俯视角生存游戏。局内升级已经存在 `UpgradeDefinition`、`RunBuildModel` 和 `GameManager.apply_run_upgrade()`，但奖励界面只硬编码“伤害/移速”两个按钮，且缺少对更多 Buff 效果的运行时消费与状态展示。

本阶段解决三个互相关联的用户体验问题，同时保持既有生存、灾难、地图、库存、Boss 和存档规则不变。

## 2. 目标

1. 增加正式启动流程，游戏冷启动先进入开始界面，不自动创建新局。
2. 提供新局、继续游戏、难度选择和退出入口；继续游戏只在存在有效安全退出快照时可用。
3. 让 `Camera2D` 始终跟随玩家，保留世界边界，增加适度平滑，兼容出生点和多地图恢复。
4. 将现有升级雏形扩展为数据驱动的局内 Buff 系统：每次升级随机产生四个不同候选，选择一个后持续到本局结束。
5. 局内不使用 Buff 等级，使用普通/稀有/史诗/传说品质；重复获得同一 Buff 时在图标上显示次数 `+1`，并按品质和次数聚合效果。
6. 加入局内幸运属性，幸运提高高品质候选的抽取权重；刷新能力不进入局内候选池，只能由首页局外成长提供且有等级上限。
7. 让 Buff 通过 `RunBuildModel` 保存和查询，由玩家、战斗、生存模块消费；UI 只发送选择命令和展示只读状态。
8. 保持旧的 `build` 快照区域和现有伤害/移速升级资源可恢复。

## 3. 非目标

- 不新增 Autoload、插件、外部依赖或网络同步。
- 不重做生存、灾难、敌人、地图生成、Boss、库存或复活规则。
- 不引入技能树、稀有度、随机抽卡、临时 Buff 持续时间或局外成长。
- 不改变“每个区域最多选择一次强化并在选择后清除区域”的核心流程。
- 不把领域规则写入 HUD、按钮脚本或 Presenter。

## 4. 现有实现复用

### 4.1 数据定义

继续使用 `scripts/data/upgrade_definition.gd` 作为静态 Buff 定义。现有字段 `id`、`display_name`、`description`、`effect_type`、`amount` 保持兼容；通过扩充枚举增加实际需要的效果类型，并增加 `quality`、`quality_weight` 和 `max_stack` 字段。旧资源不需要迁移即可继续通过校验，缺失品质按普通处理。

首版 Buff 池包含：

| ID | 类型 | 首层效果 | 叠加方式 | 消费方 |
|---|---|---:|---|---|
| `damage` | 伤害倍率 | +20% | 次数叠加 | 玩家攻击 |
| `move_speed` | 移速倍率 | +15% | 次数叠加 | 玩家移动 |
| `max_stamina` | 最大体力 | +15 | 次数叠加 | 玩家体力模型/玩家 HUD |
| `stamina_regen` | 体力恢复倍率 | +20% | 次数叠加 | 玩家体力模型 |
| `survival_efficiency` | 饥饿与水分消耗倍率降低 | -10% 消耗 | 次数叠加并设置下限 | GameManager 生存 tick |
| `luck` | 幸运 | +8 | 次数叠加 | 局内候选品质抽取 |

首版仍使用“正数代表强化量”的资源约定；消耗减缓由明确的倍率查询转换为 `max(0.5, 1.0 - amount)`，避免资源定义出现负数而破坏现有校验语义。品质枚举固定为普通、稀有、史诗、传说，品质只改变该 Buff 的基础效果档位和抽取权重，不产生独立的 Buff 等级。

### 4.2 运行时构筑

继续使用 `scripts/progression/run_build_model.gd` 保存运行时 Buff。模型维护：

- 各效果的聚合值。
- 每个 Buff ID 的品质和重复次数。
- 当前局幸运值和局外初始 Buff 的注入结果。
- 快照/恢复所需的既有 `damage_multiplier`、`move_speed_multiplier` 和 `upgrade_stacks` 字段。

新增聚合值写入同一个 `build` 字典区域，并在恢复时对缺失字段使用默认值，以兼容旧安全退出存档。非法、负数、未知效果和超过叠加上限的定义必须拒绝且不改变已有状态。

GameManager 增加只读查询出口：

- `get_run_max_stamina_bonus() -> float`
- `get_run_stamina_regen_multiplier() -> float`
- `get_run_survival_consumption_multiplier() -> float`
- `get_run_upgrade_stacks() -> Dictionary`（返回深拷贝，只读；值为 Buff 次数）
- `get_run_buff_summary() -> Array[Dictionary]`（用于 HUD，返回深拷贝）
- `get_run_luck() -> float`

现有 `get_run_damage_multiplier()`、`get_run_move_speed_multiplier()` 和 `get_run_upgrade_stack()` 保持不变。

### 4.3 效果消费

- 玩家创建 `StaminaModel` 时读取最大体力加成；每帧更新时传入体力恢复倍率。玩家速度继续通过现有移速倍率出口读取。
- 玩家攻击继续通过现有伤害倍率出口读取。
- `GameManager.tick_survival()` 将基础难度消耗倍率乘以 Buff 的生存消耗倍率。
- 升级候选模型使用当前局幸运值调整品质权重；候选中不出现刷新 Buff。
- 所有消费均通过公共查询方法完成，不访问 `RunBuildModel` 私有字段。

## 5. 启动流程设计

新增 `scenes/flow/start_screen.tscn` 与脚本，成为 `project.godot` 的 `run/main_scene`。启动界面包含：

- 游戏标题和当前版本信息。
- 难度三选一，默认普通。
- “开始游戏”：调用 `GameManager.start_run(selected_difficulty)`，成功后进入第 1 层目录场景。
- “继续游戏”：仅当 `GameManager.has_valid_run_snapshot()` 为真时启用，调用 `GameManager.restore_safe_exit_to_scene()`。
- “退出”：调用 `get_tree().quit()`。
- “成长”：进入局外成长面板，使用现有局外结晶升级初始 Buff 和刷新能力；初始 Buff 采用一个装备槽，只有装备中的一项会在下一局开始时注入本局。

启动界面不自动调用 `start_run()`。世界场景保留对旧测试和直接加载场景的兼容：只有在非启动流程测试场景中检测到运行状态为空闲时才允许自动准备，正式入口不会依赖该兜底行为。

## 6. 镜头设计

`Player/Camera2D` 继续作为玩家子节点，由 `WorldSceneController` 设置地图边界。场景默认值：

- `enabled = true`
- `position_smoothing_enabled = true`
- `position_smoothing_speed = 6.0`
- `drag_horizontal_enabled = false`
- `drag_vertical_enabled = false`

镜头中心直接跟随玩家，平滑只负责缓冲位置变化；不使用边缘拖拽，以保证战斗、出生点和多地图切换行为稳定。世界控制器继续在场景加载后设置 `limit_left/top/right/bottom`。

## 7. 升级选择界面

奖励界面改为由候选生成模型提供四张不同 Buff 卡片。每个候选卡片显示品质颜色、名称、描述、重复次数和本次增加量；按钮选择后仍只调用 `GameManager.apply_run_upgrade(definition)`。当前局已有 Buff 再次出现时，图标次数加一。刷新按钮只在局外成长提供的刷新次数大于零时启用，刷新消耗次数并重新生成四张候选。

界面另外提供一个紧凑的当前 Buff 列表，在区域奖励界面和玩家 HUD 中显示已获得 Buff 及层数。显示组件只订阅 `run_build_changed` 或读取公开查询，不直接修改构筑。

## 8. 状态与错误处理

- 启动界面无法加载目标场景、无法开始新局或无法恢复存档时，保留在菜单并显示可读错误提示。
- 继续游戏的快照无效时按钮禁用；恢复失败不会污染当前空闲状态。
- Buff 定义不合法、重复选择、非目标完成状态、楼层已清除或超过叠加上限时，`apply_run_upgrade()` 返回 `false`，不清层、不发出构筑变化信号。
- 新增快照字段缺失时使用首版默认值；字段类型非法则整体拒绝恢复，继续沿用现有快照恢复边界。

## 9. 测试设计

### 模型测试

- 新 Buff 类型、品质字段、未知类型和非正数拒绝。
- 首版 Buff 的聚合值、重复次数、品质和重置。
- 幸运改变品质抽取权重，刷新能力由局外等级和等级上限控制。
- 旧快照只包含原有字段时可恢复，新字段非法时拒绝。
- 生存消耗倍率、最大体力和体力恢复倍率真实影响模型结果。

### 场景测试

- 启动场景是 `project.godot` 主入口，冷启动不自动创建运行。
- 开始按钮创建运行并进入地下室；继续按钮恢复有效快照并进入记录场景；无快照时继续按钮不可用。
- 玩家场景的 `Camera2D` 已启用平滑，且世界控制器设置边界。
- 奖励界面由候选池生成四张可选 Buff 卡，选择后区域清除、Buff 重复次数增加，玩家攻击/移动/体力/生存消耗至少各验证一种效果；首页初始 Buff 只注入装备槽中的一项。
- 现有伤害和移速回归测试继续通过。

### 标准验证

继续执行模型测试、场景测试、框架资源验证、编辑器无头扫描、主场景无头启动和 `git diff --check`；另加一次 GUI 启动检查，确认菜单可见且进程正常响应。

## 10. 接口与数据影响

本阶段会增加 `UpgradeDefinition.EffectType` 枚举值、`RunBuildModel` 聚合查询、`GameManager` 只读查询和启动流程脚本。不会新增顶层存档字段；所有新增构筑状态位于既有 `survival_state["build"]` 区域，并提供旧存档默认值恢复。未来联机边界保持不变：核心 Buff 规则位于模型，UI 和节点只发出选择命令或展示状态。

## 11. 验收标准

- 冷启动显示开始界面，不再直接进入地下室。
- 开始/继续/难度选择/退出路径可用，失败路径可读且不污染状态。
- 玩家移动时镜头平滑跟随，地图边缘不越界，多地图和出生点恢复不回归。
- 奖励池不再硬编码为两个按钮，至少五种 Buff 可选择。
- Buff 选择后真实影响对应的玩家、战斗或生存行为，并在 HUD 显示层数。
- 旧升级资源、旧快照和现有核心循环测试继续通过。
