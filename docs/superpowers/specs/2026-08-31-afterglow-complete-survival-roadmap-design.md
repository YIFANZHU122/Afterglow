# Afterglow 完整生存游戏开发路线设计

## 1. 文档目标

本设计把现有可运行灰盒推进为完整的 2D 俯视角生存 Roguelite。开发顺序围绕同一条玩家循环展开：探索有限区域、取得资源、管理饥饿和水分、制作临时生存手段、应对夜晚与灾难、完成逃生目标并进入下一张地图。

本路线不以“系统数量”作为完成标准。每个阶段必须让玩家获得新的可操作决策，并与资源、时间、风险、战斗或地图推进中的至少一项形成真实收支关系。

## 2. 当前基线

当前版本已经具备：

- 启动界面、三档难度、局外 Buff 与继续游戏。
- 玩家移动、奔跑、近战、生命、体力和基础物品栏。
- 饥饿、水分、昼夜、驻留阶段、灾难调度和环境伤害模型。
- 逃生物资、出口启动、楼层状态机、六层运行配置和最终 Boss 双路线模型。
- 威胁预算、敌人感知、固定遭遇、存档随机流和完整运行快照。
- 地下室、慈航郊外、终局核心及天气/月相表现。

当前主要问题是领域模型领先于实际玩法：资源预算没有生成可采集物，饥渴没有物品消费入口，制作与篝火不存在，威胁预算没有夜间动态刷怪器，地图 2 至 5 复用同一场景，装备、属性、负重、翻越、挖掘和游泳尚未落地。

## 3. 产品完成定义

完整首版必须满足以下体验：

1. 新局开始后，玩家没有固定补给，必须在明确公平约束下寻找容器、水源和食物。
2. 玩家可以采集、拾取、堆叠、丢弃、使用、制作和装备物品，并承担格子、重量、耐久和时间成本。
3. 白天主要用于探索和准备；夜晚迷雾分阶段扩张并从不可见合法点动态生成敌人。
4. 月相、天气、灾难和驻留超时改变资源消耗、通行、照明、敌人和路线，而不仅是画面效果。
5. 每张地图的资源有限，逃生目标公开且可达；技术和运气允许提前离开，防守只能延迟失败，不能永久消除压力。
6. 六张地图具有不同地形、资源结构、敌人组合、灾难权重和路线决策，第六图提供 Boss 战斗与环境双路线。
7. 智力、力量、体力，头/甲/裤/包，局内 Buff 和局外结晶成长各自拥有清晰边界。
8. 死亡、复活、离层、退出恢复和整局结算不会复制奖励、丢失关键状态或生成不可解地图。

## 4. 总体架构

继续遵守“输入/命令 -> 领域模型 -> 状态变化/事件 -> 场景组装 -> 表现”方向。新增系统不直接写入 HUD，也不把所有规则继续堆入 `GameManager`。

### 4.1 静态数据

使用 typed Resource 描述：

- 物品、堆叠、重量、耐久、消费和装备字段。
- 配方、工作站、材料、制作时间和属性门槛。
- 世界资源节点、采集工具、产出和再采集规则。
- 敌人职责、威胁成本、掉落表和生成标签。
- 区域资源预算、路线节点、天气权重和合法刷新点。

静态资源只保存配置，不保存数量、耐久、燃料、生命、制作进度或已采集状态。

### 4.2 运行时模型

按职责拆分为：

- `items`：物品实例、堆叠、库存、装备、耐久、掉落和消费命令。
- `player`：属性、生命、体力、生存状态、负重修正和移动能力。
- `world`：资源节点、火源、天气、水位、迷雾、生成导演、路线和地图验证。
- `combat`：近战、远程、弹药、噪音、状态效果、敌人职责和掉落资格。
- `progression`：局内属性点、Buff、结晶、配方解锁和难度锁定。
- `core`：运行状态、确定性随机、快照聚合、离层和结算。

`GameManager` 保留跨场景协调职责；每个新规则先落在独立模型或服务，再由它组装和转发。不会先做一次高风险的全量重构。

### 4.3 存档版本

每个新增运行时系统必须同时定义快照字段、缺省恢复、非法数据拒绝和旧快照迁移策略。新版本首次引入物品实例 schema 时提高快照版本；后续阶段只追加兼容字段，除非计划明确批准迁移。

### 4.4 数值配置

所有可调数值集中到 typed Resource 或专用配置脚本。代码只保留结构性常量和安全上限。文档中的首版数值进入默认配置，测试验证边界和关系，不把所有调参值写死成脆弱断言。

## 5. 阶段路线

### 阶段 A：可操作的生存经济

#### 计划034：物品、库存与世界采集基础

建立物品实例、数量堆叠、重量、8 格基础容量、可采集资源节点和存档边界。难度按现有配置影响资源丰富度。交付木材、石料、野生食物原料和基础零件的采集与拾取。

#### 计划035：食物、饮水、容器与疾病闭环

让饥饿和水分第一次拥有真实玩家操作入口。交付食物、生肉/熟肉、生水/净水、容器容量、饮食浪费、疾病和恢复效果。

#### 计划036：制作、篝火、火把与基础建筑

交付配方系统、制作中断、篝火放置/点燃/燃料/加工、火把照明以及最小防雨设施。雨天不会熄灭篝火，但提高燃烧速度。

### 阶段 B：夜晚压力与战斗生态

#### 计划037：夜晚迷雾、月相与动态刷怪

交付迷雾三阶段扩张、合法刷新点、持续生成导演、四类夜晚规则、无月标记和保护区验证。

#### 计划038：敌人生态、远程武器、噪音与掉落

交付至少三种职责敌人、一种特殊怪、枪械/弹药/换弹、统一噪音事件、材料和结晶掉落预算。

### 阶段 C：构筑与携带决策

#### 计划039：属性、装备、负重与成长

交付开局 10 点分配、智力/力量/体力、头/甲/裤/包、8/10/12 格容量、重量惩罚、局内继承和局外阶级奖励。

### 阶段 D：地图能力与灾难反制

#### 计划040：翻越、挖掘、游泳与路线系统

交付 step 高度、水深、可挖地块、体力与工具消耗、能力路线和基础路线可达性验证。

#### 计划041：天气、灾难玩法效果与反制

交付普通天气的真实数值/地形效果、普通灾难多解、困难灾难单一主应对、并发可解性和设施生成验证。

### 阶段 E：完整内容与交付质量

#### 计划042：六图区域差异化与路线生成

交付六张具有独立资源、敌人、天气、灾难、路线和逃生目标配置的地图；第六图完成 Boss 表现与双路线通关。

#### 计划043：平衡、引导、可访问性与发布验收

交付完整新手引导、输入反馈、难度曲线、调试遥测、性能预算、长局稳定性、存档兼容、失败恢复和发布候选验收。

## 6. 依赖顺序

强制主链为：

`034 -> 035 -> 036 -> 037 -> 038 -> 039 -> 040 -> 041 -> 042 -> 043`

原因：后续系统必须消费前序已经稳定的物品、库存、制作、照明、生成、装备和路线接口。允许在不改变公共契约的情况下并行准备美术资源，但不得提前把未完成阶段的临时字段写入存档或场景契约。

## 7. 每阶段统一执行门槛

每个子计划必须：

1. 先写失败测试，再实现最小行为。
2. 更新 typed Resource 校验和内容资源清单。
3. 覆盖正常、边界、空数据、重复调用、非法状态、资源不足和恢复路径。
4. 更新运行快照和旧存档兼容测试。
5. 运行模型、场景、框架、编辑器扫描、主场景启动和 `git diff --check`。
6. 进行至少一次真实可玩验证，不只检查节点存在。
7. 更新官方计划、索引、数值文档和任务报告后才能标记完成。

## 8. 非目标与约束

- 首版保持纯单机，不实现网络同步。
- 不引入插件、第三方玩法框架或新的万能 Autoload。
- 不追求无限程序生成；先完成确定性、可验证的有限区域网络。
- 不在资源循环完成前扩展大量 Buff、敌人皮肤或装饰性地图。
- 不允许随机失败破坏唯一通关路线。
- 地狱难度允许灾难数量无上限，但仍必须通过组合合法性和可解性验证。

## 9. 验收节奏

每完成一个子计划生成一个可运行版本。阶段 A 完成后形成“基础生存演示版”；阶段 B 完成后形成“夜晚压力演示版”；阶段 D 完成后形成“系统完整 Alpha”；阶段 E 完成后形成首个发布候选版本。

## 10. 决策记录

### 2026-08-31：优先补核心循环而非继续扩展表现

- 结论：先完成资源、消费、制作和夜间生成，再开发属性、地形能力与更多内容。
- 理由：当前主要问题是模型与玩家操作断开，而不是缺少视觉系统。
- 影响：计划034 至 037拥有最高优先级。

### 2026-08-31：总计划固定目标，实施计划逐阶段细化

- 结论：所有子计划现在固定范围、依赖和验收；任务级代码步骤在进入对应阶段时基于最新接口编写。
- 理由：提前写死数月后的代码路径会与前序真实实现偏离。
- 回滚条件：只有核心玩法方向变化或前序阶段证明架构不可行时，才修订后续计划，并追加决策记录。
