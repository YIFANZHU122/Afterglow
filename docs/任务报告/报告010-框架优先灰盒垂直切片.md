## 2. 完成内容

- 使用 `AreaDefinition`、`EncounterDefinition` 和 `EncounterSpawnDefinition` 配置地下室区域及两个敌人生成项。
- 使用 `EncounterMember` 统一敌人击败事件和经验奖励，使用 `EncounterController` 维护生成、目标进度和完成事件。
- 使用 `UpgradeDefinition` 和 `RunBuildModel` 保存本局伤害/移速强化，不把运行时状态写回共享 Resource。
- 目标完成后显示一次性奖励选择；选择有效强化后才进入 `FLOOR_CLEAR`，出口在此之前保持锁定。
- 玩家攻击伤害和移动速度读取本局倍率；`reset_run()` 会清空本局构筑。
- 玩家和追击敌人通过 Presenter 语义接口发送移动、攻击、受击和死亡表现事件；缺少 Presenter 时只警告，玩法继续运行。

## 4. 接口与数据变化

- `EncounterController.start(encounter_definition: Resource, content_root: Node2D) -> bool`：从静态配置实例化有效遭遇成员；重复开始、空配置和空根节点会拒绝。
- `EncounterController.progress_changed(completed: int, target: int)`、`reward_earned(amount: int)`、`completed`：分别发布目标进度、经验奖励和遭遇完成事件。
- `GameManager.apply_run_upgrade(definition: Resource) -> bool`：仅在目标完成且本区域尚未选择奖励时接受一次合法强化，并在成功后清除区域。
- `GameManager.get_run_damage_multiplier() -> float`、`get_run_move_speed_multiplier() -> float`、`get_run_upgrade_stack(id: StringName) -> int`：提供只读本局构筑状态。
- `GameManager.is_floor_clear() -> bool`：供出口和 UI 查询正式区域清除状态。
- `ActorPresenter` 语义：`set_movement(direction)`、`play_attack(direction)`、`play_hit()`、`set_dead(dead)`；不包含玩法判定。
- 未新增 Autoload、插件、外部依赖、网络抽象或存档字段；旧楼层状态名称保留兼容。

## 6. 风险与遗留问题

- 当前奖励池固定为伤害和移速两项；随机权重、稀有度、技能树和多选规则应在玩法确定后另建计划。
- 当前地下室是唯一接入 `AreaDefinition` 的区域；后续地图组织方式变化时复用 Area/Encounter 契约，不需要把核心接口改成塔层专用名称。
- Presenter 目前只提供灰盒动画/闪烁反馈；正式美术到位后可替换实现和节点引用，不改战斗、移动和状态规则。
- 工作区保留计划 001-009 及用户的既有未提交修改；本任务未执行重置、清理或提交。

## 7. 结论

计划010完成。项目已具备一条可玩的框架优先灰盒垂直切片：区域配置生成遭遇，击败目标获得经验，完成目标后选择一次局内强化，强化生效后清除区域并允许继续流程。
